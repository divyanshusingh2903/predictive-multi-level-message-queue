# Broker and queue internals

This is a code-oriented map of the core broker and implemented Phase 2 ingress feature capture. It describes the present behavior of [`HarbingerService`](../src/harbinger_service.cpp), [`MultiLevelQueue`](../src/queue/multi_level_queue.cpp), and the [gRPC contract](../proto/harbinger.proto). Producer and consumer integration examples live in [producers.md](producers.md) and [consumers.md](consumers.md).

## Components and boundaries

```text
Producer::send → Broker.Submit → Proxy::accept → HarbingerService::route_message
                                      │                       │
                                      │              MultiLevelQueue (queued)
                                      │                  │            │
                                      │        Broker.Pull        queued TTL → DLQ
                                      │                  │
                                      │          in-flight lease
                                      │                  │
                                      └── message ID     ├── Ack → completed
                                                         ├── Nack → requeue / DLQ
                                                         └── lease timeout → requeue / DLQ
```

| Component | Responsibility |
|---|---|
| `proto/harbinger.proto` | `harbinger_rpc::Broker` methods: producer/consumer registration, Submit, Pull, Ack, Nack, InspectDlq. The wire package differs from the `harbinger` C++ namespace. |
| `src/proxy/proxy.cpp` | Create the message ID, stamp `arrival_time`, set `__producer_id`, forward to a sink; no queue scheduling decisions. |
| `HarbingerService::route_message` | Resolve per-message/default TTL, apply static priority/retry budget, and optionally capture ingress features. Future classifier injection point. |
| `MultiLevelQueue` | Thread-safe FIFO priority levels, optional aging thread, and a deadline index for positive-TTL queued messages. |
| `HarbingerService` | Registration sets, Pull selection, ownership/lease tracking, serialized settlement, bounded completion history, maintenance loop. |
| `DeadLetterQueue` | FIFO in-memory storage of expired/exhausted work; read-only paginated RPC inspection. |

There is **one logical work queue per service instance**, not per producer or consumer. Consumers are tier-blind and compete for deliveries; there is no exchange, fan-out subscription, or replayable event log. The current broker never classifies jobs by processing cost; all submissions start at `default_priority` (1 by default). Calling this an MLFQ-inspired queue refers to priority levels and promotion, **not preemption or time-slicing of handlers**.

## Message state and metadata

```text
SUBMITTED → QUEUED → IN_FLIGHT ── Ack ──→ DONE
                   │      │
                   │      ├─ Nack / lease timeout, budget left ──→ QUEUED
                   │      └─ TTL / failure budget exhausted ──→ DLQ
                   └─ queued TTL expired ──→ DLQ
```

`Message` in [`include/queue/message.hpp`](../include/queue/message.hpp) stores:

- `id`: stable across retry/redelivery; generated by the proxy as a steady-clock nanosecond value plus a process-local counter. Do not interpret it as a calendar timestamp.
- `payload`, `headers`: opaque bytes and copied string metadata. Proxy overwrites the reserved `__producer_id` header.
- `arrival_time`: set once at ingress; all TTL decisions use this steady-clock time, including after retries.
- `priority`: current level, where **0 is highest** and `num_levels - 1` lowest. `original_priority` records submit-time priority and is restored on requeue.
- `enqueue_time`: when the message most recently entered its level; reset on enqueue and aging promotion. Unlike `arrival_time`, this measures wait time *at the current placement*. Cancelled-selection restoration preserves it, so rolling back a dequeue does not restart aging.
- `ttl`: 0 disables expiry; positive durations expire at `arrival_time + ttl`. Unset requests use the server default. Negative TTL on Submit is rejected.
- `retry_count`, `max_retries`: failure accounting; successful delivery does not increase `retry_count`. The first failed delivery increments it to 1.
- `routing_context`: optional `shared_ptr<const ml::RoutingContext>` containing a bounded immutable ingress snapshot and static decision. It remains broker-only and survives retry, aging, restoration, and DLQ placement/copies.

Attempt tokens, lease deadlines, and completion records belong to broker delivery state, **not** to `Message` or its headers. A redelivery has the same message ID and a different attempt token. This distinction is what fences a late Ack/Nack after the lease has expired.

## Ingress and queueing

1. `RegisterProducer` creates a process-local `producer-<counter>` ID. `Submit` requires an ID in the registration set; registration is not authentication.
2. `Submit` copies protobuf bytes and headers, rejects negative `ttl_ms`, and calls `Proxy::accept`.
3. The proxy stamps `id`, `arrival_time`, and `__producer_id`; absent TTL is a temporary `kTtlUnset` sentinel passed only to `route_message`.
4. `route_message` assigns `default_priority` to both `priority` and `original_priority`, assigns `default_max_retries`, resolves the TTL sentinel, optionally captures ingress features/context, and enqueues once.
5. `enqueue` checks priority in `[0, num_levels)`, resets `enqueue_time`, appends to that level's FIFO list, updates the optional expiry index, and notifies a waiting dequeuer.

With the default settings the levels look like this:

```text
Level 0 (highest): [A, B]     dequeue order within level: A → B
Level 1:           [C, D]     chosen only when level 0 is empty
Level 2 (lowest):  [E]
```

`try_dequeue` / `dequeue` inspect levels from 0 upward and remove the front of the first nonempty level. There is **strict priority between levels** and FIFO within each level at the instant of selection. A newly arrived high-priority message can be selected ahead of an older low-priority message; work already dispatched to a handler is not preempted. Today normal Submit traffic all starts on the same configured level; other levels become relevant through optional aging (and a future routing classifier).

### Opt-in ingress features

`HarbingerConfig::ingress_features` is optional and programmatic. When present, a validated schema allowlists bounded numeric/categorical headers and captures exact payload byte count. Extraction and deterministic size validation run before enqueue, outside broker locks. Unknown categories remain valid values; invalid individual values have explicit missing reasons. Complete feature overflow leaves null features and an explicit validity reason without altering submission/priority semantics.

Context records disabled/static mode and actual ingress priority; model/prediction/fallback/inference-time fields are absent. Retries and aging never re-extract it. The configured schema is owned by the broker, independent of caller mutation. No capture means no context allocation. This is in-memory capture, not a feedback writer, and no standalone feature flag or ML service exists yet. See [feature configuration and Python encoding](../analysis/README.md).

### Aging

By default `aging=nullopt`, so no aging thread runs: sustained high-priority traffic can starve lower levels. When enabled, `AgingConfig` has `threshold` (default field value 5000 ms) and `interval` (500 ms). On each interval, the aging thread visits levels from lowest to level 1 under the queue mutex. It caches each level's earliest possible promotion deadline and skips levels with no due candidate. A due level is still scanned in **FIFO order** in full: a live eligible message is spliced to the **back** of the next higher level (for example, 2 → 1); its `priority` changes, its `enqueue_time` resets to the scan time, and `original_priority` stays put. Each message promotes at most one step per scan and waits a fresh threshold before another promotion. Expired messages are never promoted.

The cache takes O(number of levels) storage. Enqueue, restoration, and promotion update its minimum; removing a candidate can leave an earlier conservative deadline, costing an extra scan but never delaying eligible work. Due scans recompute the minimum from retained live work; an empty level clears it. Deadline arithmetic is checked before clock conversion/addition: an unrepresentable aging delay has no reachable promotion deadline. FIFO placement is not timestamp order because concurrent enqueue and front restoration can reorder timestamps, so scanning cannot stop at the first young message. Complexity is O(levels + nodes in due levels), and dense-due levels still hold the mutex for full scans. A separate condition variable prevents an enqueue notification from waking the aging thread instead of a waiting consumer.

### Queue TTL and expiry index

Only **queued positive-TTL** messages appear in a deadline-ordered multimap. The per-level FIFO lists have stable nodes; each indexed node retains a handle to its expiry entry through aging splices. Dequeue or removal erases the handle. TTL-off messages are not indexed and are not scanned by Pull's maintenance operation.

`sweep_expired_batch(maintenance_batch_size)` removes at most the configured number of due entries, **in deadline order**. Pull invokes one batch per polling iteration, then checks cancellation/deadline and dequeues. The background queue TTL sweeper invokes bounded batches at `ttl_sweep_interval` (100 ms by default); setting that interval to **0 only disables background queued-TTL sweeping**. The public `sweep_expired()` API is a diagnostic/test-oriented full scan preserving priority-level/FIFO order; it is unsuitable for service hot paths, which exclusively use bounded batches. A selected message is also checked for expiry before dispatch, so a message expiring between batch cleanup and dequeue goes to `TTL_EXPIRED` and Pull keeps looking.

TTL counts from original arrival rather than from requeue or promotion. Queue sweeps and aging are serialized by the queue mutex; aging skips not-yet-due levels but still scans due levels fully. With a large expired backlog, background reclamation takes several bounded passes, so the time to clear it grows with backlog. The broker does not scan in-flight messages on the queue TTL schedule: in-flight TTL is checked on settlement or lease reclamation.

## Pull and delivery ownership

`RegisterConsumer` creates `consumer-<counter>`. The Pull wait is `min(requested_timeout > 0 ? requested_timeout : max_pull_wait, max_pull_wait)`; the default cap is 5000 ms. Pull checks `ServerContext::IsCancelled()` around its loop, waits in up-to-100 ms chunks, and returns `timed_out=true` if no deliverable message arrives by its deadline.

After selecting a message and checking TTL, Pull rechecks cancellation under the in-flight mutex immediately before installing ownership. If cancellation is already observed, it returns `CANCELLED` and restores the live message through `MultiLevelQueue::requeue_front()`: no lease, completion record, or retry increment is created. A deadline-expired client may observe `DEADLINE_EXCEEDED` instead of the server's cancellation status. Selected work already expired at the TTL check still goes to `TTL_EXPIRED` rather than being restored.

Restoration inserts at the **front of the current priority level**, retaining original priority, retry count, arrival/TTL, and enqueue time; it rebuilds the positive-TTL index entry and wakes a dequeuer. It differs from ordinary Nack/lease requeue, which appends at original priority and resets aging time. Time spent temporarily selected still counts toward aging, and TTL keeps its original deadline even if it expires during restoration. FIFO is preserved relative to remaining work in that level, but restoration cannot undo messages already selected by other consumers, concurrent aging, or reordered concurrent restorations.

On a live selected message, the service stages the response directly from the locally owned payload/headers outside the settlement lock, without intermediate payload/header container copies. It then performs the final cancellation check and installs an in-flight entry keyed by message ID (message, consumer owner, token, lease deadline). Cancelled restoration clears the staged response. The broker retains the original message for redelivery; protobuf response storage still needs its own copy. The lease begins when the broker records the delivery; losing the Pull response does **not** undo it. The deadline-ordered in-flight index has an entry per delivery. `queue_size()` excludes in-flight messages; `in_flight_count()` measures current owned deliveries.

Cancellation can still occur after the final check and before response delivery. There is no separate consumer receipt-confirmation handshake, so the broker cannot distinguish a delivery never received from one received by a stalled/crashed handler. This residual window uses ordinary lease recovery: the message is temporarily in-flight, and lease expiry consumes a retry unless TTL expiry takes precedence. The cancellation check narrows this window; it does not guarantee that every abandoned Pull avoids a lease or retry charge.

The bundled client makes one Pull per worker at a time, invokes a callback, and sends Ack/Nack. It reports `processing_time_ms` for the callback duration. Embedded brokers can optionally [persist accepted observations and actual outcomes](feedback.md). Prediction and learning remain planned; telemetry never changes delivery disposition.

## Settlement, retries, and DLQ

Ack and Nack check the registered consumer, token syntax, and ownership. Under the in-flight mutex they first look for an existing completion for that token, then compare it with the live attempt (if any). Deadline checks also happen here, so an expired lease is rejected even before the maintenance thread runs. The lock order for a live settlement is **in-flight/settlement → queue or DLQ**; queue methods do not acquire the settlement lock. The broker records one completed outcome per attempt and removes its lease index entry. This serializes concurrent Ack/Nack/reclamation for the same attempt.

| Situation | Transition / caller result |
|---|---|
| Ack before lease expiry, TTL still live | Remove in-flight; Ack OK |
| Ack before lease expiry, TTL expired | Move to DLQ `TTL_EXPIRED`; Ack still OK |
| Nack before lease expiry, TTL expired | Move to DLQ `TTL_EXPIRED`; no retry increment; Nack OK |
| Nack before lease expiry, TTL live | Increment retry count once; requeue at `original_priority` or DLQ `MAX_RETRIES_EXCEEDED`; Nack OK |
| Lease expires, TTL expired | DLQ `TTL_EXPIRED`, without incrementing retry count |
| Lease expires, TTL live | Increment failure count once; requeue at original priority or DLQ |
| Settlement with already-expired lease | `FAILED_PRECONDITION` (lease transition may be performed by the request itself) |

After a non-TTL failure the broker increments `retry_count`, then tests `retry_count >= max_retries`. With default `max_retries=3`, the first two failures requeue and the third goes to DLQ. Nack re-enqueues at the **tail** of `original_priority`, resetting `enqueue_time`; its arrival/TTL do not reset. The maintenance loop checks due leases every `lease_sweep_interval` (default 100 ms) and processes at most `maintenance_batch_size` per pass, independent of queued TTL sweeping. A slow or crashed consumer can therefore have its message redelivered, possibly while its original callback is still running.

The completion map/list keeps accepted Ack/Nack and expired-attempt outcomes for up to `completion_retention` (default 60000 ms) and `completion_cache_max_entries` (10000). Repeating the same accepted operation for the same owner/token/message returns OK without requeueing or recording another failure, including after the next delivery has begun. A conflicting operation or known expired attempt returns `FAILED_PRECONDITION`; wrong owner returns `PERMISSION_DENIED`, invalid/missing token `INVALID_ARGUMENT`, and unknown delivery `NOT_FOUND`. Retention and capacity eviction can remove replay history, but a stale token cannot settle a **different live attempt**. Unknown history is **not** evidence that Ack succeeded. Only the first accepted request determines the recorded outcome and any DLQ details; replay does not repeat the mutation or emit another feedback event. Processing time is excluded from completion records but may be persisted in the first outcome's optional feedback record.

`DeadLetterQueue` retains a FIFO list of entries with the original message, DLQ reason, details, and steady-clock DLQ time. `InspectDlq` returns a **non-destructive** page with total size: limit `<=0` becomes 10, maximum 100; negative offset becomes 0. The RPC requires no registration/authentication. `dlq_age_ms` is time since entry, not a wall-clock timestamp. The internal DLQ also has a `pop()` method, but the inspection RPC never calls it; there is no DLQ redelivery RPC.

## Delivery guarantees and limits

- **At-least-once during a broker process lifetime:** lease recovery can redeliver abandoned attempts; app-side work may happen twice. Attempt tokens protect broker settlement, not external side effects. No lease renewal exists; choose a lease longer than callback duration plus network/settlement overhead.
- **Settlement replay is bounded; ambiguity can remain:** the bundled consumer retries the identical Ack/Nack on transient `UNAVAILABLE`/`DEADLINE_EXCEEDED` outcomes (up to three calls). The broker replays accepted outcomes while their completion records remain. Retention starts at recorded settlement/reclamation and capacity can evict records earlier; neither retention nor replay survives restart. After history disappears, the request can return `NOT_FOUND` or `PERMISSION_DENIED` depending on current ownership, without confirming whether an earlier request succeeded.
- **Fencing is separate from consumer availability:** a stale token cannot settle a different live attempt after history eviction, but the bundled client only recovers automatically from settlement `FAILED_PRECONDITION` (one `leases_lost()` increment, no confirmed outcome). Other final settlement errors stop it; there is no automatic restart or re-registration. See the [consumer system boundary](consumers.md#system-boundary-delivery-safety-and-consumer-recovery) for late-request results and operator responsibilities.
- **Submit ambiguity remains:** a lost Submit response can leave a queued message with an ID the producer never received. There is no producer idempotency key or publish deduplication.
- **Process-local state only:** queue, DLQ, registered IDs, leases, and completions are not persisted. Restart does not recover messages. There is no replication, multi-queue routing, authentication/TLS on the bundled clients and server, capacity/backpressure, or ML classifier yet.

## Configuration and places to change behavior

[`HarbingerConfig`](../include/harbinger_service.hpp) sets the defaults below (all durations are milliseconds):

| Setting | Default | Effect |
|---|---:|---|
| `num_levels` | 3 | Priority levels, 0 highest |
| `default_priority` | 1 | Static submit-time priority; must be `< num_levels` |
| `aging` | `nullopt` | Disabled; when enabled uses positive threshold and interval |
| `default_max_retries` | 3 | Failure budget before DLQ |
| `default_ttl` | 0 | TTL from arrival; 0 disables |
| `max_pull_wait` | 5000 | Maximum server Pull wait |
| `ttl_sweep_interval` | 100 | Queued TTL background cleanup; 0 disables background TTL only |
| `delivery_lease` | 30000 | Fixed in-flight lease duration |
| `lease_sweep_interval` | 100 | Recovery cadence independent of TTL sweep |
| `completion_retention` | 60000 | Completion replay duration, subject to capacity |
| `completion_cache_max_entries` | 10000 | Replay cache capacity |
| `maintenance_batch_size` | 256 | Max queued TTL / lease removals per maintenance batch |
| `ingress_features` | `nullopt` | Opt-in versioned, immutable static ingress snapshots; embedded configuration only |

The standalone server and demo explicitly **enable aging**; constructing `HarbingerService{}` does not. For routing changes, start at `route_message()` in `src/harbinger_service.cpp`. For scheduling/expiry behavior, inspect `MultiLevelQueue`. For delivery ownership and retry policy, inspect `HarbingerService::Pull`, `settle`, `finish_locked`, and `run_maintenance`; for callback behavior, inspect `Consumer::run`. The integration tests in `tests/unit/test_broker.cpp` and `tests/unit/test_client.cpp` exercise the broker over a real gRPC server despite their directory name.
