# Project state and recommended roadmap

## Summary
PMLMQ has a substantial Phase 1 in-memory C++20/gRPC broker, while its predictive-ML claim and benchmarking are still planned. First establish the current uncommitted Phase 1 changes as a verified baseline; then choose between research integration and production hardening.

## Context / Findings
- `README.md` describes Phase 1 as complete and identifies `route_message()` plus Ack/Nack `processing_time_ms` as Phase 2 hooks.
- `src/pmlmq_service.cpp`, `src/queue/`, `src/proxy/`, and client libraries implement submit/pull/ack/nack, priority scheduling, optional aging, retry/DLQ, TTL, registration, and in-flight ownership.
- The ML engine, feature extraction, feedback persistence, model bridge, classifier, drift metrics, and benchmark harnesses/baselines do not yet exist.
- The current tree has extensive uncommitted changes, including TTL/DLQ behavior, tests, and an untracked CI workflow; historical test output predates those changes.
- The broker remains an in-memory prototype without leases/redelivery recovery, bounds/backpressure, durable state, security, or operational telemetry.

## Approach
Treat Phase 1 correctness as the immediate milestone. Verify and review the present worktree before growing scope, because routing research relies on trustworthy delivery semantics and benchmark results require a stable baseline. Afterwards, pursue ML routing in shadow mode with static-priority fallback and reproducible baselines; defer production hardening unless deployment is the intended outcome.

## Files affected
- `README.md` — reconcile the documented status and configuration defaults after Phase 1 verification.
- `.github/workflows/ci.yml` — include the current CI workflow in version control and make verification reproducible.
- `tests/unit/test_broker.cpp` — extend service-level regression coverage for TTL, ownership, cancellation, and failure boundaries.
- `tests/unit/test_client.cpp` — cover client RPC failure/recovery and pull-timeout behavior.
- `src/pmlmq_service.cpp` — future Phase 2 routing and feedback integration point; no change until the baseline is verified.

## Step-by-step implementation
1. Build from a clean directory and run the unit and integration suites for the current worktree; repeat under ASan and UBSan, then run the thread sanitizer for queue/service concurrency.
2. Review and commit the existing TTL/DLQ/proto/test/CI work as one coherent Phase 1 milestone only after the checks pass.
3. Add missing focused regressions for wrong-owner Ack/Nack, Pull cancellation and capped waits, concurrent expiry/ownership transitions, shutdown, and failed Ack/Nack paths.
4. Correct the `AGENTS.md` aging-default inconsistency with `PMLMQConfig` and ensure README implementation status matches verified behavior.
5. Define Phase 2 contracts: versioned safe-to-log feature schema, feedback record keyed by message ID/outcome, bounded classifier deadline, static-priority fallback, and shadow-mode observation.
6. Implement predictive routing behind `route_message()` only after those contracts exist; retain the Phase 1 static policy as a switchable baseline.
7. Add reproducible synthetic and trace-replay workloads plus FIFO, static-priority, and round-robin comparisons before evaluating P50/P95/P99 or the research hypothesis.
8. If deployment becomes the goal, separately prioritize lease/redelivery, bounded queues and backpressure, durability, TLS/authentication/authorization, idempotency, health endpoints, metrics, and tracing.

## Risks / edge cases
- Unverified uncommitted changes may invalidate the stated Phase 1 completion claim.
- TTL, in-flight ownership, background sweeping, and retries interact under concurrency; classifier work could hide their failures.
- Predicted routing without a timeout/fallback can degrade latency or availability.
- Benchmark outcomes are not meaningful without comparable workload definitions, baselines, and repeatable environments.

## Testing strategy
- Clean Release build plus `ctest --test-dir build --output-on-failure`.
- Separate ASan, UBSan, and TSan configurations.
- Run the end-to-end demo and integration tests after protocol/service changes.
- For Phase 2, evaluate routing in shadow mode before activation and report prediction error, P50/P95/P99, throughput, and starvation against baselines.

## Open questions
- Is the desired near-term outcome a research demonstration of predictive scheduling or a deployable message broker?
- Should the currently uncommitted Phase 1 changes be treated as the intended baseline to validate and commit?
