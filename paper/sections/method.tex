\section{Evaluation method}\label{sec:method}

A scheduling claim is easy to overstate, so we fixed what would count as success before running the experiments that
support it. Each experiment has a configuration and a set of pass criteria committed to the repository before its first
registered run, and the commit that froze them is recorded alongside the results. A criterion compares an arm against a
baseline as a paired difference, per seed or per time window, with a bootstrap 95\% interval, and a gate passes only when
every primary criterion does. Concretely, for a metric $M$ such as mean latency, the unit of pairing is a seed (or, in a simulation, a time window) $u$, and a
relative-delta criterion is the average of the paired differences,
\begin{equation}
  \Delta \;=\; \frac{1}{|U|}\sum_{u\in U}\frac{M_u^{\text{arm}}-M_u^{\text{FIFO}}}{M_u^{\text{FIFO}}},
  \label{eq:delta}
\end{equation}
with its interval taken by resampling the units; a ratio criterion averages $M_u^{\text{arm}}/M_u^{\text{FIFO}}$ in the same way. Slowdown is a job's
latency divided by its own service time. The primary criteria concern mean latency and the median latency of short jobs. All-message
P99 and the longest wait of a long job are guardrails, which a design must not break, and are not goals. We should be
honest about the limits of this discipline: the budgets for the first experiment were chosen after we had seen data
from an earlier offline study, so they are not independent of it. Deviations from the pre-registrations are listed here. Every frozen configuration is unchanged since the commit that froze it. One amendment was
made during the AWS runs: the single-host replication moved to its own instance when the vCPU quota rose, before its first run and with only message counts read. The thirty-minute run
was registered as descriptive, with no gate. The first trace simulation on Azure, before the weighted design, used older simulator rules, and a staleness defect
found there was fixed before the later experiments; the common-rules runs on Azure use the converted trace and time-based windows, so their figures differ slightly. The DAS2
diagnosis and the quiet-machine re-run were run afterwards and are not pre-registered, and the re-run keeps the frozen configurations and analysis.

The arms follow the questions the experiments ask. FIFO is the default behaviour of most queues. Two static-priority
baselines stand for what an operator would do by hand: one set by someone who knows each job type's cost, and one set badly
but plausibly, in which an expensive and a cheap job share a level. Shadow mode measures the cost of prediction without its
effect, and predictive mode routes by prediction, with or without job-type labels. An oracle that ranks messages by their
true planned cost shows how much room a perfect predictor would leave. We treat the oracle as a reference rather than an
optimum, since it ranks by fixed terciles and costs are only approximate under contention.

The main workload is a synthetic production flow that we designed to look like the background work of an online shop. Five
services produce nine job types, from cheap jobs such as stock reservation to long report exports, and
the handlers do real CPU work through the real producer and consumer clients. Load follows a steady phase at about
sixty percent utilisation, a flash-sale overload at about one hundred twenty-five percent, a recovery, and a mid-run change
in job costs, with about thirty-five thousand messages per run and five seeds. We ran it locally, on a laptop with turbo disabled (Section~\ref{sec:results} gives the conditions), then on AWS with the
broker and the clients on separate hosts (\texttt{c8i.xlarge} and \texttt{c8i.2xlarge} instances in one placement group),
and replicated the original single-host run on a second instance of the larger type. The same workload then ran against
RabbitMQ with FIFO, with static priorities, and with \sys{}'s predictor acting as a sidecar that sets the priorities, and
against Redis with FIFO, with the same producers, handlers, workers, arrivals and seeds so that only the broker and its
policy change. A thirty-minute run, in two repetitions, tests whether the benefit survives long backlogs. Two further frozen production-flow experiments test the design's optional features: one compares weights and pausing aging with predictive routing under the default aging, and one tests keys split by input size. An offline comparison of eight online learners against per-key statistics, on recorded workloads, decided whether a model was needed at all.

Real traces test what a synthetic workload cannot: whether keys recur and how heavy the tails are in practice. A
discrete-event simulator replays the Azure Functions 2021 trace \citep{zhang2021harvest} (its earlier characterisation is \citet{shahrad2020}), the Huawei Cloud public request traces (2025 release; the earlier trace study is \citealt{joosen2024}) and two Parallel
Workloads Archive logs \citep{feitelson2014} at offered loads of 0.5, 0.8 and 0.95, using the same predictor code as the broker and a common
trace format. Arrivals are reconstructed where a trace lacks them, and one of the traces records completion times instead
of arrival times, which we discuss with the limitations. Two gates are defined for each trace. Gate~A asks whether
predictive routing, as built and with the default aging, beats FIFO. Gate~B asks the same of the design with weights
and pausing aging. Every number in this section and the next is generated from the committed result files by a script in
the paper's repository, and the guardrails are judged on the upper end of their intervals.
